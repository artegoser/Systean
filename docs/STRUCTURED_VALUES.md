# Structured Values: Numbers, Quantities, and Time

Status: **Phase 6–8 executable specification**

This document defines the package-backed structured-value layer implemented by `systean-core`. These values are not ordinary lexical roots. They are parsed and generated by generic codecs owned by the language package, then lowered into the same typed semantic IR as lexical expressions.

The canonical configuration lives in:

- `language/literals.toml` — numeric and temporal surface forms;
- `language/units.toml` — dimensions, unit identities, spoken forms, written symbols, and exact conversion ratios;
- `language/semantics/core.semsys` — semantic types and temporal relations.

The fixed Systean alphabet remains unchanged. Spoken structured-value forms are validated against the same phonology as ordinary roots.

---

## 1. Structured-literal boundary

`LiteralEngine` implements the generic `StructuredLiteralCodec` contract:

```text
surface tokens
    -> structured literal codec
    -> canonical typed StructuredLiteral
    -> ordinary semantic checking/elaboration
```

Every accepted structured literal carries:

- a family identity;
- one canonical semantic payload;
- one declared semantic type;
- canonical written form;
- canonical spoken form.

Parsing a value and converting/evaluating that value are separate operations. The parser never silently changes units, fills missing temporal context, or converts one structured type into another.

## 2. Exact numbers

### 2.1 Type split

The numeric subsystem keeps these semantic values distinct:

```text
Number
Digit
DigitSequence
```

A bare numeral denotes `Number`. `Digit` is the typed component used by the digit-sequence subsystem. `DigitSequence` preserves a sequence of decimal digits, including leading zeroes. There is no implicit `Number <-> DigitSequence` coercion.

Examples:

```text
5                         Number(5)
dig 005                   DigitSequence("005")
dig nul nul pent          DigitSequence("005")
```

### 2.2 Written exact numbers

Canonical written numbers use Arabic decimal notation when the exact rational has a finite decimal expansion; otherwise they use an exact fraction.

Supported exact written input includes:

```text
5
-25
1.25
1/3
1.2e6
```

Approximation is deliberately outside the exact `Number` codec.

### 2.3 Spoken digits

```text
0  nul
1  uno
2  dva
3  tri
4  kvar
5  pent
6  siks
7  sev
8  okt
9  nin
```

### 2.4 Sparse magnitude-first integers

Canonical integer speech announces each non-zero magnitude **before** its coefficient. Missing magnitude terms are omitted rather than spoken as zero padding.

Coefficient magnitudes:

```text
dek   10^1
hek   10^2
```

Direct outer magnitudes:

```text
kilo  10^3
mega  10^6
giga  10^9
tera  10^12
peta  10^15
eksa  10^18
zeta  10^21
yota  10^24
rona  10^27
keta  10^30
```

Examples:

```text
pent
= 5

dek dva
= 20

hek kvar pent
= 405

kilo dva dek dva pent
= 2,025

mega uno pent
= 1,000,005

mega uno kilo pent sev
= 1,005,007
```

The listener receives the large scale before its coefficient: `mega ...` immediately establishes a million-scale term.

Outer magnitudes above `10^30` use one canonical greedy composition. For example:

```text
keta mega uno
= 10^36

keta keta keta giga dek uno
= 10^100
```

Alternative magnitude chains that denote the same exponent are rejected instead of becoming synonyms.

### 2.5 Decimal, rational, and exponent forms

Selected support forms:

```text
minus  negative sign
plus   explicit positive sign
dot    exact decimal point
rat    exact rational constructor
eks    explicit decimal exponent constructor
```

Scoped constructors use the ordinary `ki ... ku` structural delimiters:

```text
rat ki uno ku ki tri ku
= 1/3

eks ki uno dot dva ku ki siks ku
= 1.2 * 10^6
```

For very small finite decimals, canonical speech may use `eks` instead of forcing long runs of spoken zeroes. This is a deterministic rendering decision controlled by `literals.toml`; it does not make the underlying value approximate.

## 3. Quantities and units

### 3.1 Generic semantic model

Units and quantities are dimension-typed:

```text
Unit<D>
Quantity<D>
Approximate<Quantity<D>>
```

The initial package declares the SI base dimensions needed by the current language layer:

```text
LengthDimension
TimeDimension
MassDimension
TemperatureDimension
CurrentDimension
AmountDimension
LuminousIntensityDimension
```

A unit value, a number, and a quantity are different semantic types.

### 3.2 Unit registry

`language/units.toml` declares:

- stable unit identity;
- dimension identity;
- canonical written symbol;
- canonical spoken Systean form;
- exact rational scale relative to the dimension's canonical unit.

The initial registry includes meter/kilometer/centimeter, second/millisecond/hour, kilogram/gram, kelvin, ampere, mole, and candela.

Written SI symbols are technical notation and are not required to be Systean lexical roots. Spoken unit forms are validated by the fixed Systean phonology.

Examples:

```text
5 m          <-> pent metr
1 km         <-> uno kilometr
```

### 3.3 Exact conversion is explicit

Parsing preserves the authored unit identity:

```text
1 km
```

remains `1 km` after parsing. Conversion is a separate operation, for example through:

```text
systean literals convert 1 km --to meter
```

Exact rational conversion metadata prevents floating-point drift:

```text
1 km      -> 1000 m
100 cm    -> 1 m
1/3 m     -> 100/3 cm
```

Conversion across incompatible dimensions is rejected.

### 3.4 Approximation and uncertainty

Approximation is explicit:

```text
~5 m
apro pent metr
```

Explicit symmetric uncertainty is also preserved:

```text
1±0.1 km
apro ki uno ku ki nul dot uno ku kilometr
```

Uncertainty is converted by the same exact scale as the measured value. Approximate quantities remain typed as approximate after conversion.

## 4. Time and calendar values

### 4.1 Semantic split

The temporal subsystem distinguishes:

```text
Temporal
Instant <: Temporal
Interval <: Temporal
CalendarDate <: Temporal
TimeOfDay <: Temporal
Duration
TimeZone
```

`Duration` is not an `Instant`, and an `Interval` is not inferred from a duration. The parser never introduces tense from word order.

### 4.2 Written forms

Canonical written forms are deterministic:

```text
2026-08-11                         CalendarDate
12:34:56                           TimeOfDay
+03:00                             TimeZone
2026-08-11T12:34:56+03:00          Instant
PT3600S                            Duration
2026-08-11T12:00:00Z/2026-08-11T13:00:00Z
                                   Interval
```

Instants require an explicit timezone.

### 4.3 Spoken forms

Selected structural support forms:

```text
dat   calendar/time constructor
zon   timezone constructor
```

Variable-width calendar fields are placed in explicit `ki ... ku` scopes so a listener never has to guess where a year ends and a month begins.

Example date:

```text
2000-12-31
<-> dat ki kilo dva ku ki dek uno dva ku ki dek tri uno ku
```

Canonical duration speech chooses a configured time unit deterministically to avoid unnecessarily long numeric values. For example:

```text
PT3600S
<-> dat ki uno ku hor
```

### 4.4 Temporal relations

Selected lexical forms are ordinary typed relations:

```text
ante   before
aft    after
pot    during
```

The semantic package also exposes an explicit interval-duration relation. Temporal relations operate on explicit temporal values and remain independent of Phase 9 aspect/event-target semantics.

### 4.5 `nau` and the context provider

`nau` denotes the context key `now` and has type `Instant`. It never reads a system clock from the sentence parser.

The runtime context provider already supplies typed values for context lexemes such as:

```text
speaker     used by mi
addressee   used by tu
now         used by nau
```

A context value is required exactly when a surface expression uses its context lexeme. Different explicit `now` values therefore change semantic resolution, not syntax or parse rules.

No place-context lexeme has been authored yet. If one is added later, it must use the same explicit typed provider contract rather than implicit geolocation or world knowledge.

## 5. CLI inspection

Structured values can be inspected without embedding them in a sentence:

```text
systean literals analyze 1000005
systean literals analyze 5 m
systean literals analyze 2026-08-11T12:34:56+03:00
```

Exact quantity conversion is explicit:

```text
systean literals convert 1 km --to meter
```

The discourse playground can install an explicit structured temporal context:

```text
context-surface now 2026-08-11T12:00:00Z
analyze nau ante 2026-08-12T00:00:00Z
```

## 6. Phase 6–8 invariants

The implementation is required to preserve all of these properties:

1. Exact numeric parsing never silently introduces approximation.
2. `Number`, `Digit`, and `DigitSequence` remain type-distinct.
3. Canonical integer speech is sparse and magnitude-first.
4. Zero magnitude terms are omitted rather than used as padding.
5. Accepted magnitude chains have one canonical decomposition.
6. Structured literals use the same semantic type checker as lexical expressions.
7. `Number`, `Unit<D>`, and `Quantity<D>` are distinct.
8. Unit conversion is explicit and dimension checked.
9. Exact unit conversions use rational arithmetic.
10. Approximation/uncertainty remains explicit through conversion.
11. Absolute temporal literals round-trip deterministically.
12. `nau` depends only on an explicit typed context value.
13. Temporal relations add no hidden tense or aspect inference.
14. Spoken support forms must remain valid under the fixed Systean phonology and must not collide with lexical or structural forms.
